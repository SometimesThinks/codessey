# 외부 요청과 응답 흐름

## 전체 흐름

1. **주소 확인:** 사용자가 브라우저에 `https://codyssey.duckdns.org` 입력, DNS 조회를 통해 서버의 퍼블릭 IP 확인
2. **서버 연결:** 확인한 IP의 HTTPS 포트인 443번으로 연결 요청, 인터넷 게이트웨이를 통한 EC2 접근
3. **접근 허용 확인:** 네트워크 설정과 보안 그룹 규칙에 따라 해당 연결의 통과 여부 결정
4. **컨테이너 전달:** EC2의 443번 포트로 들어온 연결을 Docker 포트 매핑에 따라 Nginx 컨테이너의 443번 포트로 전달
5. **암호화 연결:** 브라우저의 서버 인증서 검증과 Nginx와의 TLS 연결 수립
6. **페이지 요청:** 암호화된 연결을 통해 브라우저에서 메인 페이지 `/` 요청 전송
7. **내용 조회:** Nginx에서 웹 루트에 있는 `index.html` 파일의 내용 `Hello Cloud (Docker)` 조회
8. **응답 반환:** Nginx에서 같은 연결을 통해 `HTTP 200`과 본문 `Hello Cloud (Docker)` 반환, 브라우저에서 결과 표시

일반 HTTP 접속은 80번 포트 사용 및 인증서 검증·TLS 연결 단계 생략. 퍼블릭 IP 직접 접속은 도메인의 DNS 조회 단계 생략

## 1. 도메인에서 목적지 IP 확인

1. 브라우저 또는 `curl`에서 `codyssey.duckdns.org` 조회
2. DNS 캐시에 유효한 정보가 없을 때 DNS 리졸버를 통한 주소 확인
3. DuckDNS에 등록한 A 레코드에 따라 `43.203.235.49` 반환
4. 확인된 IP를 목적지로 웹 연결 시작

**DuckDNS의 역할:** 무료 서브도메인과 DNS 제공. 웹 요청을 대신 받거나 EC2로 중계하는 프록시 역할은 미수행

퍼블릭 IP 직접 접속인 `http://43.203.235.49/health`에서는 해당 도메인의 DNS 조회 단계 생략

## 2. 인터넷에서 EC2까지 연결

| 구성 요소        | 요청 처리에서의 역할                                | 실습 설정                                |
| ---------------- | --------------------------------------------------- | ---------------------------------------- |
| Internet Gateway | VPC의 인터넷 연결 및 EC2 퍼블릭·프라이빗 IPv4 매핑  | `codyssey-igw`, VPC 연결                 |
| Public Subnet    | EC2가 위치하는 네트워크 구간                        | `10.0.1.0/24`                            |
| Route Table      | 목적지에 따른 전달 경로 결정, 인터넷 응답 경로 제공 | `10.0.0.0/16 → local`, `0.0.0.0/0 → IGW` |
| Security Group   | EC2 연결 허용 여부 판단                             | TCP 80·443 전체 IPv4, TCP 22 본인 IP/32  |
| EC2 네트워크     | 허용된 요청 수신                                    | 프라이빗 IP `10.0.1.205`                 |

인터넷 연결에는 IGW 연결, 서브넷 라우팅, 퍼블릭 IP, 허용된 보안 규칙 및 수신 서비스가 함께 필요. 라우팅 테이블은 요청이 방문하는 별도 서버가 아닌 경로 설정

서브넷 Network ACL도 패킷 통과 조건에 포함. 본 문서에서는 실제 실습에서 별도 변경을 기록하지 않은 기본 구성으로 구분

## 3. Docker 포트 매핑을 통한 전달

| 외부 요청 | EC2 호스트 포트 | 컨테이너 포트 | 처리                       |
| --------- | --------------- | ------------- | -------------------------- |
| HTTP      | 80              | 80            | 평문 HTTP 요청 처리        |
| HTTPS     | 443             | 443           | TLS 연결 후 HTTP 요청 처리 |

- 컨테이너 이름: `codyssey-web`
- 이미지: `nginx:stable-alpine`
- 포트 매핑: `-p 80:80 -p 443:443`
- EC2 호스트에 설치했던 Nginx: 중지·자동 시작 해제 상태
- 최종 웹 요청 처리 주체: Docker 컨테이너 내부 Nginx

[컨테이너 실행 명령과 검증 기록](../04_Docker/docker.md) 참조

## 4. HTTPS 연결과 인증서 확인

1. TCP 연결 이후 클라이언트와 컨테이너 Nginx 간 TLS 연결 수립
2. Nginx에서 `codyssey.duckdns.org`용 인증서 제시
3. 클라이언트에서 도메인 일치·유효기간·인증서 신뢰 체인 확인
4. TLS 연결 성공 후 암호화된 `GET /health` 전송

- TLS 종료 위치: Docker 컨테이너 Nginx
- 인증서: Let’s Encrypt 발급
- 인증서 경로: `/etc/letsencrypt/live/codyssey.duckdns.org/fullchain.pem`
- 인증서 개인 키: 서버 내부 사용, 제출 자료에 내용 미포함

HTTP 80 요청은 TLS 과정 없이 처리. 본 실습에서는 HTTP를 HTTPS로 강제 전환하지 않고 두 방식 모두 응답 유지

## 5. 요청 경로에 따른 파일 조회

Nginx의 웹 루트 `/usr/share/nginx/html`에 호스트의 `/home/ubuntu/codyssey-web` 디렉터리를 읽기 전용으로 마운트한 구성

| 요청 경로 | 호스트 파일                            | 컨테이너에서 조회하는 파일         | 검증 응답                     |
| --------- | -------------------------------------- | ---------------------------------- | ----------------------------- |
| `/`       | `/home/ubuntu/codyssey-web/index.html` | `/usr/share/nginx/html/index.html` | `200`, `Hello Cloud (Docker)` |
| `/health` | `/home/ubuntu/codyssey-web/health`     | `/usr/share/nginx/html/health`     | `200`, `OK`                   |

`/health`는 애플리케이션이나 데이터베이스 상태를 검사하는 프로그램이 아닌 정적 파일 응답. 파일이 없으면 404 발생 가능

EBS는 EC2의 웹 파일·설정 등이 저장되는 스토리지이며, 외부 HTTP 요청을 직접 수신하는 서버와 구분

## 6. 외부 클라이언트로 응답 반환

1. Nginx에서 상태 코드·헤더·본문 생성
2. HTTPS 연결인 경우 TLS 암호화 적용
3. Docker 네트워크와 EC2를 거쳐 인터넷 목적지로 응답 전달
4. 서브넷 기본 경로와 Internet Gateway를 통해 외부 클라이언트에 반환
5. 브라우저의 화면 표시 또는 `curl`의 응답 출력

Security Group은 상태를 추적하므로 허용된 연결의 응답 트래픽 허용. 왕복 통신에는 라우팅 및 Network ACL 조건도 충족 필요

## 웹 요청과 별개인 관리 작업

| 항목          | 역할                                                     |
| ------------- | -------------------------------------------------------- |
| IAM           | AWS 콘솔·API에서 EC2·VPC 등을 생성·조회·삭제할 권한 관리 |
| SSH 22        | 관리자의 EC2 로그인과 서버 내부 명령 실행                |
| Certbot       | 인증서 발급·갱신 수행                                    |
| certbot.timer | 인증서 갱신 작업의 주기적 실행                           |
| 갱신 훅       | 갱신 성공 후 Nginx 설정 검사·reload 수행                 |

Certbot과 Let’s Encrypt는 인증서 발급·갱신 과정에 참여하며, 일반 웹 요청마다 경유하는 구성 요소는 아님. IAM 사용자 정책은 AWS 관리 작업 권한이며 방문자의 웹 접속 허용은 SG·네트워크·웹 서버 설정에서 처리
